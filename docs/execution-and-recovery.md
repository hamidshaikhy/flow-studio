# اجرا و بازیابی

## حالت‌ها

اجرای تازه پس از اعتبارسنجی به running می‌رود. هر بلوک ابتدا pending است؛ ثبت شروع آن را running می‌کند، سپس commit نتیجه آن را succeeded می‌کند. شاخهٔ غیرفعال skipped می‌شود و عملیاتش فراخوانی نمی‌شود. خطای فعال، اجرای کل را failed می‌کند و مراحل بعدی pending می‌مانند. Cancel بلوک‌های انجام‌نشده را cancelled می‌کند.

Pause یک درخواست توقف است که در مرز بلوک اعمال می‌شود؛ UI تا آن مرز «در حال توقف» نشان می‌دهد. Step دقیقاً یک بلوک واجد شرایط را انجام می‌دهد. ادامهٔ اجرای terminal مجاز نیست؛ اجرای دوباره شناسهٔ تازه و snapshot تازه دارد. یک pump فعال، شروع یا ادامهٔ تکراری را رد می‌کند.

## ترتیب ثبت

1. snapshot نسخه‌دار گردش‌کار و node stateهای اولیه در یک تراکنش ذخیره می‌شود.
2. ورودی و زمان شروع بلوک ثبت و commit می‌شود.
3. عملیات بیرون از تراکنش انجام می‌شود؛ تراکنش در طول fetch یا delay باز نیست.
4. خروجی، شاخه، زمان پایان و وضعیت در یک رکورد commit می‌شود.
5. فقط بعد از موفقیت مرحلهٔ ۴، مصرف‌کنندهٔ بعدی شروع می‌شود.

`Engine.commit` از کپی پیشنهادی استفاده می‌کند. اگر ذخیرهٔ نتیجه شکست بخورد، خروجی پیشنهادشده وارد current معتبر نمی‌شود. اجرا در حافظه paused و خطای storage نمایش داده می‌شود. هنگام ادامه، مرحلهٔ ثبت‌نشده ممکن است تکرار شود. این رفتار در تست unit و خطای واقعی IndexedDB مرورگر بررسی شده است.

## بعد از تازه‌شدن صفحه

برنامه ابتدا برای دریافت قفل مالک تلاش می‌کند. اگر زبانهٔ دیگری مالک باشد، running را قطع‌شده اعلام نمی‌کند؛ زبانهٔ دوم نمی‌تواند silently اجرا را ادامه دهد. اگر مالک قبلی از بین رفته باشد، runningهای ذخیره‌شده interrupted می‌شوند.

کاربر «ادامهٔ اجرای ذخیره‌شده» را انتخاب می‌کند. موتور از snapshot همان اجرا استفاده می‌کند و succeeded و skippedها را دوباره اجرا نمی‌کند. اگر شرط قبلاً ثبت شده باشد، تصمیم مسیر آن حفظ می‌شود. GET نیمه‌تمام فقط با همین درخواست صریح ادامه تکرار می‌شود. تأخیر نیمه‌تمام نیز مدت کامل را از ابتدا طی می‌کند؛ زمان بسته‌بودن صفحه حساب نمی‌شود.

## پنجرهٔ نتیجهٔ نامشخص

بین انجام درخواست در سرور و commit پاسخ محلی، امکان بسته‌شدن صفحه وجود دارد. برای روش‌های غیر GET، بلوک interrupted با `uncertain: true` علامت می‌خورد. `resume` بدون `allowUnsafe` آن را رد می‌کند. UI هشدار روشن و تصمیم صریح برای پذیرش ریسک تکرار نشان می‌دهد. ردکردن پنجره هیچ درخواست جدیدی نمی‌فرستد.

هیچ retry خودکار شبکه وجود ندارد. حتی لغو موفق fetch تضمین نمی‌کند سرور درخواست را انجام نداده است. حفظ exactly-once به سازوکار سمت سرویس مثل idempotency key نیاز دارد و در قرارداد این فرانت‌اند نیست.

## محدودیت ذخیره و مالکیت

Web Locks قفل مشترک اجرای این origin را در طول اجرا و توقف نگه می‌دارد؛ در پایان موفق، خطا یا لغو آزاد می‌شود. بستن صفحه قفل مرورگر را آزاد می‌کند. در نبود API قفل، اجرا مسدود و دلیل نمایش داده می‌شود. قفل سند برای ویرایش چندزبانه وجود ندارد؛ یک سند را هم‌زمان در چند زبانه ویرایش نکن.

به unload برای checkpoint متکی نیستیم. آخرین چند حرف ویرایش‌شده ممکن است پیش از autosave از دست بروند؛ نشانگر «در حال ذخیره» از «ذخیره شد» جدا است. دادهٔ اجرای commitشده مستقل از این debounce ثبت می‌شود. تاریخچهٔ غیرقابل‌خواندن، quota و خطای دسترسی با پیام قابل اقدام گزارش می‌شوند؛ کاربر می‌تواند اسناد را دریافت یا داده‌های سایت را از راهنما پاک کند.
